## Summary

The permanent Teacher Onboarding Hub has been replaced with a five-step Glass Modal Wizard rendered over the existing teacher dashboard. The dashboard remains usable behind the overlay and has no onboarding checklist or resume panel after the modal is closed or onboarding is complete.

The wizard is server-eligible only for newly provisioned teacher accounts whose onboarding lifecycle is incomplete. Closing the modal preserves the server-side cursor; the next dashboard visit resumes at the last unresolved step. Completion sets `onboarding_completed = true`, after mandatory steps are resolved and optional student/schedule steps are completed or explicitly deferred.

## Implemented Behavior

1. **Peran Mengajar:** two independent switches, Guru Mata Pelajaran and Wali Kelas. The UI states these are preferences only; they do not grant permission or create assignments.
2. **Pilih Mata Pelajaran:** multi-select from active master subjects in the active tenant. Selected IDs and confirmation status are persisted; at least one selection is required when options exist. Empty master data remains a valid continue state and creates no assignment.
3. **Buat Kelas Pertama:** only Nama Kelas and Tingkat Kelas X/XI/XII. Self-service SMA tenant setup now seeds the three canonical grade levels so this step can create a valid Rombel.
4. **Tambah Siswa Pertama:** Tambah sekarang opens the existing `/data-siswa` workflow; Lewati stores a deferred state and creates no student or placement.
5. **Atur Jadwal Pertama:** Atur sekarang uses an existing official teaching assignment and the existing server action to create/publish schedule entries. Guru can add or remove multiple day/time rows in one submission; all rows are sent as `sessions[]`. Nanti saja records a defer. No synthetic assignment is created.

## Persistence, Migration, and Dependencies

- Added tenant-scoped fields to `preferensi_onboarding_guru`: first-use eligibility, completion flag, wizard cursor, selected subject IDs JSON, and subject confirmation timestamp.
- Migration is additive. Existing preference rows default to `onboarding_eligible = false` and `onboarding_completed = true`; existing users are not unexpectedly prompted.
- Newly self-registered teachers receive an eligible/incomplete onboarding row within the existing registration transaction. The admin-created login path for a teacher profile also creates the scoped onboarding row.
- Progress, cursor, preferences, defer, and completion are server-persisted per user and school. Active tenant and permission continue to come from the existing server-side session/authorization guards.
- Migration `20260929180000_add_teacher_onboarding_wizard_state` was applied to the configured local database and the isolated Vitest database.
- No dependency changes.

## Domain, Authorization, and Tenant Checks

- Role switches only persist preference fields. They do not change base role, membership, effective permission, or assignments.
- Subject selection stores tenant-validated master subject IDs only; it does not create MataPelajaran or PenugasanMengajar records.
- Class creation writes one tenant-scoped Rombel with its creator and grade. It does not synthesize subject, assignment, student, enrollment, placement, or schedule data.
- Schedule creation is accepted only through an existing official teaching assignment. The existing schedule action validates teacher ownership, active school context, active academic period, and schedule constraints.
- No changes were made to the Authorization Engine, tenant isolation rules, role-permission definitions, membership logic, or Google OAuth implementation.
